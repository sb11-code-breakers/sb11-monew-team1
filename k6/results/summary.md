## 핵심 분석

### 1. VU 증가 대비 응답시간 증가율

```text
VU  5명 →  50명 (10배): avg 12ms →  21ms (1.7배)  ← 선형 이하
VU 50명 → 150명  (3배): avg 21ms → 227ms (10배)   ← 지수적 증가!
```

VU가 3배 늘었는데 avg가 10배 증가했어.
이는 PostgreSQL JOIN 쿼리가 동시 요청에
**지수적으로 느려지는** 특성을 보여줍니다.

---

### 2. 응답시간 분포 변화

```text
        avg    p95    max
1단계:  12ms   19ms  100ms  → 안정적
2단계:  21ms   40ms  420ms  → 스파이크 시작
3단계: 227ms  588ms 2040ms  → 한계 노출
```

3단계에서 **max가 2,040ms**까지 치솟았습니다.
p(95)는 임계값(2,000ms) 이내지만
5%의 요청은 588ms~2,040ms 사이에 분포하여
응답시간 편차가 매우 커졌습니다.

---

### 3. PostgreSQL JOIN 병목 원인

`GET /api/user-activities/{userId}` 는 매 요청마다
5개 쿼리를 순차 실행합니다:

```text
1. users 조회
2. subscriptions JOIN
3. comments JOIN
4. comment_likes JOIN
5. article_views JOIN
```

150명이 동시에 호출하면 순간적으로
**750개 쿼리**가 PostgreSQL에 쏟아집니다:

```text
커넥션 풀 고갈
    ↓
대기 중인 요청들이 큐에 쌓임
    ↓
앞 요청 완료까지 대기
    ↓
5개 JOIN 쿼리 순차 실행
    ↓
2,040ms
```

### 4. 로컬 환경임에도 한계 노출

현재 테스트는 PostgreSQL, Spring Boot, k6가
**모두 같은 컴퓨터**에서 실행된 로컬 환경입니다:

```text
내 컴퓨터 (Windows)
├── Docker → PostgreSQL 컨테이너
├── Spring Boot 앱 (bootRun)
└── k6 테스트 스크립트
```

- 네트워크 지연 = 거의 0ms (localhost)
- 데이터가 RAM 캐시에 올라가 있는 상태
- 실제 프로덕션보다 훨씬 유리한 조건

실제 프로덕션(AWS ECS + RDS) 환경 예상:

```text
현재 로컬 3단계: avg 227ms, max 2,040ms
실제 AWS 예상:   avg 500ms+, max 5초+
```

### 5. MongoDB 전환 근거 및 가설

**현재 PostgreSQL 방식:**

```text
5개 JOIN 쿼리 → O(n)
데이터/동시요청 증가에 비례해서 느려짐
```

> ⚠️ 아래 수치는 실측값이 아닌 **예상치**입니다.
> 실제 MongoDB 구현 후 동일한 k6 스크립트로 검증이 필요합니다.

| 항목    | PostgreSQL (실측) | MongoDB (예상) | 개선 예상 |

| avg   | 227ms           | 10~30ms      | 약 10배 |

| max   | 2,040ms         | 100ms 이하     | 약 20배 |
