## 상세 분석

### 1. 측정 대상 API 내부 동작

`GET /api/user-activities/{userId}` 호출 시 PostgreSQL에서
아래 5개 쿼리가 순차적으로 실행됩니다:

```text
1. users 조회
2. subscriptions JOIN   (유저당 10개)
3. comments JOIN        (유저당 최대 10건)
4. comment_likes JOIN   (유저당 최대 10건)
5. article_views JOIN   (유저당 최대 10건)
```

150명이 동시에 이 API를 호출하면 순간적으로
PostgreSQL에 **750개 쿼리**가 동시에 쏟아집니다.

---

### 2. avg = 227.02ms — 2단계 대비 10배 증가

```text
1단계 avg  12ms  ██░░░░░░░░░░░░░░░░░░
2단계 avg  21ms  ███░░░░░░░░░░░░░░░░░
3단계 avg 227ms  ████████████████████
```

VU가 50명 → 150명으로 3배 늘어났는데
avg는 21ms → 227ms로 **10배** 이상 증가했어.

이는 PostgreSQL JOIN 쿼리가 동시 요청에 선형이 아닌
**지수적으로 느려지는** 특성을 보여줍니다.

---

### 3. max = 2,040ms — 순간 최대 지연 관찰

**현상**: 최대 응답시간이 2,040ms로 관찰되었습니다.
임계값으로 설정된 지표는 아니지만 성능 저하의 신호입니다.

**원인**: 150명이 동시에 피크를 찍었을 때:

```text
커넥션 풀 고갈
    ↓
대기 중인 요청들이 큐에 쌓임
    ↓
앞 요청 완료까지 대기
    ↓
5개 JOIN 쿼리 순차 실행
    ↓
2,040ms
```

**MongoDB 전환 명분**: MongoDB는 `user_activities` 도큐먼트를
단건 lookup으로 조회하므로 VU가 150명이 되어도
이런 커넥션 풀 고갈과 쿼리 경합이 발생하지 않을 것으로 예상됩니다.

---

### 4. p(95) = 588.42ms — 응답 분포 불안정

```text
avg  227ms  ████░░░░░░░░░░░░░░░░
p90  476ms  ████████░░░░░░░░░░░░
p95  588ms  ██████████░░░░░░░░░░
max 2040ms  ████████████████████
```

95%의 요청이 588ms 안에 응답했지만
나머지 5%는 588ms ~ 2,040ms 사이에 분포합니다.
이는 부하가 집중될 때 **응답시간 편차가 매우 크다**는 것을 의미합니다.

---

### 5. TPS = 160/s — 처리량의 한계

```text
이론 최대 TPS: 150명 × 2회/초(sleep 0.5초) = 300 TPS
실제 TPS: 160/s
```

이론값의 절반 수준만 처리했어. 이유는:

```text
요청 처리 시간 227ms + sleep 500ms = 727ms
→ 실제 iteration 730ms
→ 유저당 초당 약 1.37회 요청
→ 150명 × 1.37회 = 약 205 TPS (실제 160 TPS)
```

처리 시간이 길어질수록 TPS가 자연스럽게 제한됩니다.

---

### 6. data_received = 212MB — 응답 데이터 폭증

```text
1단계: 32MB  (3,462건)
2단계: 32MB  (3,462건)
3단계: 212MB (14,451건) ← 약 6.6배 증가
```

요청당 약 14.7KB로 2단계(9.2KB)보다 커졌어.
유저당 구독(10개), 좋아요(20개), 조회(10개)가 늘어난 만큼
응답 JSON 크기도 커졌기 때문입니다.

---

### 7. 로컬 환경임에도 한계 노출

3단계에서 **로컬 환경임에도 불구하고** max 2,040ms가 나왔어.
실제 프로덕션(AWS ECS + RDS) 환경에서는:

```text
현재 로컬: avg 227ms, max 2,040ms
실제 AWS:  avg 예상 500ms+, max 예상 5초+
```

네트워크 지연, 디스크 I/O, 커넥션 풀 경합이 추가되면
성능 저하가 훨씬 심각해질 것입니다.

---

### 8. MongoDB 전환 시 예상 효과 (가설)

현재 PostgreSQL:

```text
5개 JOIN 쿼리 → O(n) → 데이터/동시요청 증가에 비례해서 느려짐
```

[가설] MongoDB 전환 후:

```text
단건 document lookup → O(1) → 데이터/동시요청 증가에 무관하게 일정할 것으로 예상
```

> ⚠️ 아래 수치는 실측값이 아닌 **예상치**입니다.
> 실제 MongoDB 구현 후 동일한 k6 스크립트로 검증이 필요합니다.

| 항목    | PostgreSQL (실측) | MongoDB (예상) |
|-------|-----------------|--------------|
| avg   | 227ms           | 10~30ms      |
| p(95) | 588ms           | 30~50ms      |
| max   | 2,040ms         | 100ms 이하     |
| 실패율   | 0%              | 0%           |
