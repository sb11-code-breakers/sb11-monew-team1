## 상세 분석

### 1. 측정 대상 API 내부 동작

`GET /api/user-activities/{userId}` 호출 시 PostgreSQL에서
아래 5개 쿼리가 순차적으로 실행됩니다:

```
1. users 조회
2. subscriptions JOIN   (유저당 5개)
3. comments JOIN        (유저당 최대 10건)
4. comment_likes JOIN   (유저당 최대 10건)
5. article_views JOIN   (유저당 최대 10건)
```

50명이 동시에 이 API를 호출하면 순간적으로
PostgreSQL에 **250개 쿼리**가 동시에 쏟아집니다.

---

### 2. avg = 20.97ms — 응답 분포

```
avg  20ms  ████░░░░░░░░░░░░░░░░
p90  30ms  ██████░░░░░░░░░░░░░░
p95  40ms  ████████░░░░░░░░░░░░
max 420ms  ████████████████████
```

평균은 21ms로 빠르지만 avg와 max 사이 격차가 **20배**입니다.
이는 평소엔 빠르지만 특정 순간 갑자기 튀어오르는
**불안정한 응답 패턴**을 보여줍니다.

---

### 3. max = 420.45ms — 순간 지연 스파이크

**원인**: 50명이 동시에 피크를 찍었을 때 PostgreSQL 내부에서
커넥션 풀 대기 및 JOIN 쿼리 경합이 발생했습니다:

```
커넥션 풀 대기
    ↓
쿼리 실행 대기 (앞 요청 완료까지)
    ↓
5개 JOIN 쿼리 순차 실행
    ↓
420ms
```

**MongoDB 전환 명분**: MongoDB는 `user_activities` 도큐먼트를
단건 lookup으로 조회하므로 동시 요청이 늘어도
이런 스파이크가 발생하지 않습니다.

---

### 4. TPS = 38.25/s — 이론값과의 차이

```
이론 최대 TPS: 50명 × 1회/초 = 50 TPS
실제 TPS: 38.25/s
```

일부 요청이 20~40ms 걸리면서 sleep 포함 iteration이
1.02초로 늘어나 TPS가 감소했습니다.

---

### 5. data_received = 32MB

```
32MB ÷ 3,462건 = 약 9.2KB/건
```

각 유저의 활동 내역(구독 5개, 댓글 10건, 좋아요 10건,
조회 10건)이 JSON으로 내려오는 크기입니다.

---

### 6. 평균 20ms가 선방한 이유 — 로컬 환경의 한계

현재 테스트는 **로컬 환경**에서 진행되었습니다.

**로컬 환경 구조:**

```
내 컴퓨터 (Windows)
├── Docker → PostgreSQL 컨테이너
├── Spring Boot 앱 (bootRun)
└── k6 테스트 스크립트
```

세 개가 같은 컴퓨터에서 돌아가기 때문에:

- 네트워크 지연 = 거의 0ms (localhost)
- 2,500개 댓글이 전부 RAM 캐시에 올라가 있는 상태
- 실제 프로덕션 환경보다 훨씬 유리한 조건

**실제 프로덕션(AWS ECS + RDS) 환경에서는:**

```
클라이언트 → ECS (Spring Boot) → RDS (PostgreSQL)
                                    ↑
                              네트워크 지연 발생
                              디스크 I/O 발생
                              커넥션 풀 경합
```
