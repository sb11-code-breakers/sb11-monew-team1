## 상세 분석

### 1. 실패 17건 분석 — 동시성 제어 한계

**현상**: `POST /comment-likes` 1,692건 중 17건 실패 (약 1%)

**원인**: 50명의 VU가 동시에 요청을 보내는 과정에서, 서로 다른 두 유저가
찰나의 순간에 완전히 동일한 댓글에 동시에 좋아요를 누르는 타이밍이
17번 발생했습니다. PostgreSQL의 UNIQUE 제약 조건에 의해 중복 INSERT가
거부되면서 에러가 발생한 것입니다.

**MongoDB 전환 명분**: MongoDB는 도큐먼트 업데이트 시 `$addToSet` 또는
`$inc` 같은 원자적(Atomic) 연산을 지원하여, 이러한 동시성 쓰기 충돌을
훨씬 유연하고 빠르게 처리할 수 있습니다.

---

### 2. max = 1,780ms — 순간 지연 스파이크

**현상**: 평균은 48ms인데 가장 느린 요청은 1,780ms(약 1.78초)가 걸렸습니다.
평균 대비 약 37배의 격차입니다.

**원인**: VU 50명이 피크를 찍었을 때, 특정 순간 PostgreSQL 내부에서
쓰기 작업(POST)에 의한 락 대기(Lock Wait)가 발생했거나,
QueryDSL 페이징 조회와 트랜잭션 커밋이 한꺼번에 몰리면서
순간적인 디스크 I/O 병목이 발생한 것입니다.

**MongoDB 전환 명분**: PostgreSQL은 읽기와 쓰기가 같은 테이블/인덱스
페이지에서 경합할 때 순간적인 성능 저하(Spike)가 큽니다.
반면 MongoDB(WiredTiger 엔진)는 대량의 동시 쓰기가 들어와도
순간 밀림 현상이 PostgreSQL에 비해 훨씬 적고 고르게 분포합니다.

---

### 3. 평균 48ms가 선방한 이유

현재 테스트는 **로컬 환경**에서 진행되었습니다.
PostgreSQL, Spring Boot, k6가 모두 같은 컴퓨터에서 실행되어
네트워크 지연이 거의 없고 DB 데이터가 메모리에 캐시된 상태입니다.

**로컬 환경 구조:**
```
내 컴퓨터 (Windows)
├── Docker → PostgreSQL 컨테이너
├── Spring Boot 앱 (bootRun)
└── k6 테스트 스크립트
```

세 개가 같은 컴퓨터에서 돌아가기 때문에:
- 네트워크 지연 = 거의 0ms (localhost)
- DB 데이터 2,500개가 RAM 캐시에 올라가 있는 상태
- 실제 프로덕션 환경보다 훨씬 유리한 조건

**실제 프로덕션(AWS ECS + RDS) 환경에서는:**
```
클라이언트 → ECS (Spring Boot) → RDS (PostgreSQL)
                                    ↑
                              네트워크 지연 발생
                              디스크 I/O 발생
                              커넥션 풀 경합
```

실제 환경에서는 네트워크 레이턴시, 디스크 I/O 증가,
커넥션 풀 경합으로 인해 본 테스트 결과보다 성능이 더 나쁠 수 있습니다.
또한 데이터 규모가 커질수록 캐시 히트율이 떨어지고 디스크 I/O가 증가하여
JOIN 쿼리의 성능 저하가 더욱 두드러질 것입니다.

## 다음 단계 — 3단계 대규모 테스트

현재 결과에서 MongoDB 전환 명분을 더욱 극적으로 증명하기 위해
3단계에서는 다음과 같이 부하를 강화합니다:

| 항목 | 2단계 | 3단계 |
|------|-------|-------|
| 유저 | 50명 | 100명 |
| VU | 50명 | 100~150명 |
| sleep | 1초 | 0.5초 |

VU 100명이 되는 순간 PostgreSQL 커넥션 풀 부족과 맞물려
최대 지연 시간이 3~4초 이상으로 치솟으며 에러율이 증가할 것으로 예상됩니다.
